# Laptop hardware commissioning

Current scope: ESP32-A, three lights, fan and gas. The user confirmed no PIR is installed; its firmware reports are disabled. The door module is deferred and unchanged. The laptop has Mosquitto 2.1.4, a restricted TLS broker, and the CP2102 driver; the connected ESP32-D0WD-V3 is on COM5.

1. The official Windows broker from https://mosquitto.org/download/ is installed under `.local/tools/mosquitto`. Anonymous access is disabled. Arduino CLI is under `.local/tools/arduino`; the classic ESP32 package is pinned to 2.0.17.
2. Connect ESP32-A using a USB data cable. Establish a stable laptop IPv4 address on the same reachable mobile hotspot as the board. At this review the laptop address is `172.20.10.5`; verify it before generating certificates.
3. The current private settings are already provisioned. For a new installation, run `scripts/prepare-lights.ps1`. It defaults to the current hotspot and `172.20.10.5`, asks for the hotspot password with hidden input, and generates a private light-controller header. Use `-BrokerIP NEW_IP -SSID HOTSPOT_NAME` after network changes. Add `-MotionSensor` only when a PIR is physically installed. The underlying `node scripts/setup-hardware.js PRIVATE_JSON` accepts `board: "lights"`, `ssid`, `wifi_password`, `broker_ip`, and `motion_enabled`; it creates a local CA, broker certificate, MQTT passwords, ACLs and `.local/hardware/hub.json`. It refuses to overwrite existing keys. Keep `.local/hardware` private and renew the broker certificate before 90 days.
4. The hardware launcher starts Mosquitto with `.local/hardware/mosquitto.conf`. The named Windows Firewall rule allows TCP 8883 only from the hotspot subnet. Do not forward the port from the router. If changing networks, update the broker certificate, private board header, listener address and firewall subnet together.
5. Run `scripts/flash-lights.ps1 -Port COMx` with the actual light-board port. It compiles before uploading and uses board `esp32:esp32:esp32`; override `-FQBN` for a different confirmed board model. `-CompileOnly` omits upload. The Arduino config keeps downloads and builds on D:. Required light-board libraries: PubSubClient and ArduinoJson. The private `homeauto_config.h` is ignored by Git. The sketch validates the broker CA and synchronizes time for TLS certificate validation.
6. Stop the existing hub. Launch `scripts/start-local.ps1 -Mode Hardware -HardwareConfig .local/hardware/hub.json`. It remembers the private gateway connection file through `.local/gateway-path.txt`; the domain account credentials are used at the laptop dashboard. If no saved pairing exists, supply `-GatewayFile PRIVATE_GATEWAY_JSON`.
7. The Modules screen should show the broker and light board online. The door and uninstalled PIR remain unavailable. All four relay channels passed live ON/OFF tests and the user confirmed physical response. Gas reports arrive every four seconds, within the application's ten-second freshness limit. Relay recovery after power loss remains a separate physical test.
8. After local verification, enable the remote lighting flags listed in `../cloud/REMOTE_HUB_ARCHITECTURE.md`. Keep all door flags off. Test the phone through the domain and confirm that the laptop receives each command once and fresh board status completes it. Shut down the laptop and confirm unavailable controls. Some mobile hotspots isolate connected clients; if the board cannot reach TCP 8883 on the laptop, verify hotspot client communication before changing application code.

The domain's **Explore demo home** remains independent of physical hardware.
