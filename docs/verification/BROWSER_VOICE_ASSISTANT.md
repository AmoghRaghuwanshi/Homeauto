## Latest follow-up: Hindi, live chat and optional wake listening

Automatic reply language now follows the recognized words, rather than the recognition locale. A shared browser/server policy detects Hindi script and a small set of clear romanized Hindi words; an English decoder hint can no longer force Hindi into an English reply. The frontend also preserves the intent's reply language when an execute response lacks a language field, and uses the resolved result language for speech. Explicit English/Hindi **Reply language** choices remain deliberate overrides; choose **Automatic** for matching replies. This does not make the browser's single-locale recognition automatically bilingual.

Assistant now has a bounded **live chat** log with separate user/reply turns, live transcript updates, language tags and preserved scroll position when reading older turns. It retains up to 40 turns in memory for the current home session; refresh, Clear conversation, account/home changes remove that history. No chat transcript is written to localStorage, IndexedDB or a database. A recognition error before any final transcript still appears as an assistant message. Starting a new turn does not erase earlier messages.

Manual microphone clicks and an explicitly started conversation always send `wake_required:false`. They never require saying Shrimaan, even when the wake setting is enabled.

**Settings → Voice & assistant → Enable wake-word listening** is a separate, opt-in listener. Enabling it starts browser continuous recognition from that gesture. While idle, only an anchored final wake phrase activates HomeAuto. Supported forms include Shrimaan, Shreeman, Shiman, श्रीमान and शिमान, optionally preceded by Hey and followed by Ji. Ambient speech, substring matches and interim wake hypotheses do not activate or send transcripts to HomeAuto. The browser's own speech provider may still receive ambient audio; the UI discloses that difference.

The idle listener releases recognition before activation. A wake-only utterance opens conversation listening; a combined wake/request forwards the request exactly once through the existing authenticated WebSocket. Subsequent conversation turns need no further wake word. Output and command processing pause the idle listener, and a 350ms quiet buffer prevents it from hearing the assistant. Ending the conversation returns to wake waiting only if that listener was explicitly started. **Stop wake listening** or disabling the setting stops it. Its status and stop control remain visible throughout the app, and idle listening can continue across normal in-app navigation.

The saved option uses the existing versioned preference key, but reload never automatically opens a microphone. Select Start wake listening after a reload. Tab hiding, logout and home/account transitions stop the active listener; they do not silently resume on return. Network/permission errors stop retries, and repeated empty browser restarts are bounded. This is foreground-page wake listening, not OS-wide or closed-tab listening. Browser support, background suspension and provider connectivity still apply.

Wake activation never changes execution permissions. Real-device voice controls retain review, ambient speech alone sends no command, and door unlocking still belongs to Security. All acceptance work uses simulated hardware and substituted browser speech APIs.

## Current implementation

This supersedes the native Whisper/Kokoro runtime and the earlier same-day offline scoped assistant report. At the user's request, HomeAuto now uses the same browser speech method described in their earlier farmer assistant: `SpeechRecognition` / `webkitSpeechRecognition` for listening, `speechSynthesis` / `SpeechSynthesisUtterance` for output, interim transcripts and an explicit repeated-turn session. This is a scoped home assistant, not a general knowledge LLM or a full-duplex Live API.

Story: Assistant → browser recognition → authenticated local `/voice` WebSocket carrying final text → existing strict parser and owned intent → protected execute API → current result → protected speech-text API → browser synthesis → 350ms quiet buffer → next listening turn, until ended.

The WebSocket carries recognized text, not microphone audio. It does not perform speech recognition. The browser manages its recognition engine and may send audio to its vendor's servers. No third-party speech API key, HomeAuto model download, Python worker or paid Live API was introduced. Browser recognition is neither guaranteed offline nor zero-latency.

## Interaction and language

- **Tap to speak** records one turn. The browser's end-of-utterance event submits final text. Interim text is visible but never executed. **Finish recording** stops recognition and waits for its final result; it does not promote an uncertain interim transcript.
- **Start conversation** listens for repeated turns. No recognizer runs while the assistant speaks. Listening resumes only after synthesis `onend`, followed by 350ms quiet. Unlike the reference's six-second watchdog, a stalled output never automatically opens the microphone. A bounded stall pauses the session.
- **End conversation**, **Stop speech**, typing, clearing, navigation, home/account changes and hiding the page cancel the active conversation and its queued restart/speech. An explicitly enabled wake listener can return to waiting after a normal turn or conversation end; its separate Stop control stops wake listening. Clearing, home/account changes and tab hiding also stop wake listening. An ordinary single-turn request already processing can still finish while hidden without playing audio. No-speech, microphone denial, network failure and unsupported output pause instead of retrying indefinitely. Goodbye ends after the final spoken reply.
- Real-device controls still require the existing review. The session pauses for that review; cancelling it cannot send a command. Unlocking still requires the separate Security flow. Simulation executes only through the fake publisher and identifies its results as demo reports.
- English and Hindi are supported. Recognition takes one locale, `en-IN` or `hi-IN`. **Automatic listening follows the app language**, while automatic replies follow recognized text. Standard Web Speech does not offer portable simultaneous English/Hindi language detection. The UI explains this rather than claiming automatic bilingual recognition.
- Output selects a matching-language browser/OS voice, preferring local service and an Indian locale. Hindi never silently falls back to an English voice. Missing voices leave text visible with recovery guidance. Newly defaulted local voice speed is 0.9; explicitly stored settings and adjustable speed remain.
- Greetings, capabilities, supported controls, status and out-of-scope guidance retain the existing bounded bilingual parser. Other languages, open-domain answers and contextual slot-filling are not implemented by copying the reference's crop parser.

## Boundaries and lifecycle

`server/lifecycle.js` now constructs `BrowserSpeechService`. Its readiness describes the hub's browser-text relay, not proof of client capabilities. The client independently feature-detects recognition, synthesis and secure context before enabling controls. The local API can still disable voice with `HOMEAUTO_VOICE_ENABLED=0`.

Voice tickets remain CSRF-protected, session-bound, one-use and short-lived. `/voice` retains origin/session checks and connection limits. Browser starts use `format: browser_text`; binary PCM is rejected. One final text message, maximum 500 characters, is allowed per utterance. Extra transcript action fields are rejected. The server returns an expiring owned intent and never executes it from the transcript message. Intent execution retains authentication, authorization, idempotency, current hardware freshness and Security restrictions. Successful browser-text sockets close after the intent.

The protected `/api/assistant/speech` route now returns `{provider:'browser', text, language, rate}` for an owned result or a fixed allowlisted prompt. It does not accept arbitrary client-provided output text. No audio job or WAV is generated. The browser speaks only the current turn, with cancellation/generation guards. The existing audio-job routes return not found in this provider. `/api/ai/models` returns an empty assets list; model activation is retired. Diagnostics and settings explain browser voice instead of requesting Local AI setup.

The `vosk` dependency and its native transitive dependencies were removed from the server manifest/lockfile with `npm uninstall --ignore-scripts`. The old downloaded weights, both native Python environments, Whisper tools and fixed-reply audio cache were moved out of `.local` to `D:/homeauto-audit-tools/retired-speech-20261115-browser`; `MOVED.json` records each source and verified destination. These files are recoverable, outside the checkout, and not loaded. Historical native worker source, validation tests, plans and dated measurements remain available for reference. Do not run the historical model provisioning scripts for this browser mode.

No firmware, MQTT topics, RFID rules, hardware publisher semantics, database schema or production configuration was changed. Remote website voice remains outside this local change; there was no deployment or Git publication.
