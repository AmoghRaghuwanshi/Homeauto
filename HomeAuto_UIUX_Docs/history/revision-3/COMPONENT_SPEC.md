# HomeAuto — reusable component contracts

Revision3, **PLANNED**, 2026-11-05. Tokens: [THEMES.md](THEMES.md). Screen composition: [SCREENS.md](SCREENS.md). Constructors return an HTMLElement plus `update(props)` and idempotent `dispose()` only where stateful. Use safe DOM creation, textContent, addEventListener; never inline onclick, arbitrary SVG/HTML, style strings derived from user input or a click on a nested button propagating to a parent link.

## Common component contract

Inputs are immutable presentation DTOs from State selectors, not raw database authorization flags. Callbacks return Promise results or navigation only; server retains policy authority. A component receives unique IDs and translated text; no storage/network directly except controllers below. Validation rejects unknown variants/icon keys and displays a fallback for missing text. Return no new production methods beyond constructors, update and dispose unless added to ARCHITECTURE. Every row inherits: no secret/audio logging; failure surfaced inline; loading label not fake timer; 48px minimum target; native keyboard semantics; rerender preserves focus; safe text rendering tests. Related test prefix COMP and corresponding UI tests in TEST_PLAN.

## Composition and shared states

All components support normal, loading, empty, error, offline, unauthorized where meaningful; inert presentational primitives do not create artificial fetch states. Compound cards show command requested→accepted/published→controller reported/uncertain using shared selectors; no component independently decides MQTT success. Error text associated to affected control survives toast dismissal. Status updates should not replace the focused card node wholesale; patch safe text/attributes or restore focus by stable control key.

Overlay behavior: one modal at a time; reauth replaces unlock dialog temporarily and returns with explicit confirmation still required. New critical sensor alert is visible above ordinary content and announced without stealing focus or silently dismissing a sensitive dialog. Dropdown menu uses native buttons, Esc/outside closes, Arrow semantics only if implementing an actual ARIA menu; simpler disclosure list is preferable.

Screen-reader labels include device display name and action: “Light 1, reported off, turn on.” For door: “Front door, controller reports locked”; detail explains no position sensor. On unknown state prefer two explicit light actions and an unavailable explanation rather than an unchecked switch that implies off. No global card click combined with switch click. Always escape labels by DOM text binding, including theme titles/settings restored from local storage.
